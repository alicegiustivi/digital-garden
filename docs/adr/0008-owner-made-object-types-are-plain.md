# The owner can make their own Object Types and choose each type's colour; a type of their own is a plain Object

The owner can now create Object Types in the app (a Book, a Place, a Recipe), and change the colour of any type, the four core ones included, from the Types page under More. A type has a name, a plural, a colour, an icon and its own properties. Nothing needs a restart, a rebuild or a CSS edit.

**Colour and icon are data.** A type stores the key of one of eighteen soft colours (`src/shared/palette.ts`) and the key of one icon. The owner chose the set (the Tailwind "100" tints, from a screenshot): each colour is the owner's pastel *fill* (chips, covers, swatches), the colour's own *ink* for icons, dots and outlines (just deep enough to be seen), and a *text* shade that is the ink made only as much darker as text needs, with a matching pair for dark mode. (The first version made the ink much darker; the owner found it too dark.) The screen writes `--t-<key>` (ink) and `--tf-<key>` (fill) from that data (`applyTypes` in `ui.tsx`), so `typeVar(type)` and every `var(--t-…)` follow the owner's choice. The palette is kept apart from the Tag colours so a type never looks like a Tag; the first four keys are the ones stored for the core types since the migration, so only their look changed (earlier muted colours, then bright, now these). The icons are a set of 49 from Hugeicons "stroke rounded" (MIT, the family already in `icons.ts`), and only those are added there. Colour is never the only signal: the icon and name always show beside it. `tests/palette.test.ts` fails if any text shade stops reaching WCAG AA (4.5:1) on every surface it sits on, its own fill included, or any ink stops reaching 3:1 as an outline, in light and dark.

**The core types keep every special behaviour.** Since the Express add-on (issue #139) there are six: Project and Piece join after Person, each with an owner-only Stage and an optional About line and nothing else, and the Archivist never works on either. Source (link reading, format, status, images), Concept (versions, the Distill desk), Thought (the owner's words only, Open Questions) and Person (portraits, descriptions) were already keyed by type name in the code, and still are. `object_types.core` marks them; they can be recoloured and reordered, nothing else. A type the owner makes is a plain Object: title, body, Tags, Connections, Private, the Bin, Search, Backup, Export, and the properties the owner chose. It gets none of the special rules (no link reading, portrait, Open Question or Concept versions). Giving a custom type more is a separate decision.

**Properties** are short text, long text or a choice from a list; one can be shown under the title. They are stored like every other field (`field_definitions`, `type_fields`, `field_values`), each under its own id, so renaming a property never loses a value. Removing one first says how many Objects have a value (Bin included) and then deletes those values; a Backup still has them. Dates and links as property kinds are a later question.

**Only the owner shapes types.** Creating, renaming, recolouring, reordering, giving properties to, moving Objects out of and removing a type are routes reached only from the Types page. No AI module imports the code (a test checks it). The Archivist keeps proposing only `source` and `person` as a change of type and never moves an Object into a custom type.

**Same AI treatment for the Objects of a custom type.** Once the owner has put an Object in a custom type, the Archivist adds Tags, adds Connections (related and authored by directly, up to the usual cap; specific kinds are Suggestions) and fills the type's properties from the Object's own text. A property value is an AI Contribution like any other: applied directly, marked ✦, undone in one click (it joins the run's single Undo), never over a value the owner wrote. Only facts the text states: a choice must be one of its options, and a short text or a choice must appear in the Object's own words (title, body, other values), checked in code, not only asked of the model; a long text is a short description the prompt keeps close to the text. Private Objects of a custom type are never read by any AI role, and Thoughts stay the owner's words only (a custom type is never a Thought).

**Removing a type.** A type with Objects, including ones in the Bin, cannot be removed: the Types page offers "Move them to another type" first (an owner act: it also clears the Archivist's earlier type change). Core types cannot be removed. The key (`x-<name>`) never changes once made, so renaming is always safe, and the database trigger that refuses an unknown type still holds. The `x-` prefix keeps a type's key from ever clashing with the screen's own CSS names (`--t-peek`, `--t-menu`).

**Capture, Export, Backup.** Capture can save words as a type of the owner's choice (words only; links and images stay Sources). Export writes a folder per type by plural name and puts each type's colour (palette key and both hex values), icon and fields in `garden.json`; the Bin stays out. A Backup copies the database, so types, properties and values come back with it; "bring back one thing" also recreates a custom type (and its properties) if it was removed since the Backup.

We chose a stored palette key over a free colour picker (a colour that fails contrast, or clashes in dark mode, cannot be chosen), and one Types page over editing inline from the type picker (reordering, recolouring and properties need room). The cost: twelve colours and a small icon set, and a custom type that is deliberately plain.
